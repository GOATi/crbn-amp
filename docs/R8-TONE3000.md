## What is settled with TONE3000's service (checked live, 2026-11-15)

- **The key.** Self-serve under the owner's account (garthmidgley), Settings, API Keys. The publishable key
  `t3k_pub_J6MuMOba14a05Nl3Luf4Mp1Zj7Ik7oPi` is the OAuth `client_id`; it is public by design and lives in the page.
  The secret key is never used: Rig is a public client (PKCE), and no secret is copied anywhere.
- **Redirects.** One registered: `https://rig.carbonlinear.com/tone3000.html`. `http://localhost` and
  `http://127.0.0.1` on any port are always allowed, so tests and the desktop app need no registration.
- **The flow works end to end:** authorize, then the token exchange, then `/user` (200, garthmidgley); a refresh
  rotates the refresh token; `/tones/favorited` 200. Access tokens last 3,600 s. No consent screen appeared for the
  key's own owner.
- **CORS is open** (`Access-Control-Allow-Origin: *`, `Authorization` and `Content-Type` allowed) on the API and on
  `/oauth/token`. So the page calls TONE3000 directly in **both** builds (the desktop page's origin is
  `https://crbn-rig.example`); there is no server of ours in between, and no native networking.
- **Always pass `architecture=2`** on `/models` and `/tones/search`: without it TONE3000 hides A2 models (a trending
  A2 tone listed `models_count: 1` and `/models` returned none). Rig's engine plays A2 (NAM Core's `a2_fast.cpp`,
  `SlimmableContainer`), A1 and custom. A1 is a separate request (`architecture=1`); a tone's per-architecture counts
  tell us which to ask for.

## The shape: a TONE3000 tab beside "My folder"

As the owner's lab drew it (`docs/design/2026-11-10-rig-lab/lab.html`, the library head: "My folder" and
"TONE3000"). The library keeps one folder source (`library.js`); TONE3000 is a second **view** in the same panel,
drawn by its own module in the library's drawings (rows, cards, shelves), not a second folder.

| TONE3000's requirement | Where Rig meets it |
|---|---|
| 1. Entry from where a tone is added or changed | The library is where captures are chosen in Rig; its head gets the TONE3000 tab. "In the rig" has a T3K-mark button beside the capture (Select with `format=nam`) and the cabinet IR (`gears=cab&format=ir`). A pedalboard one (`gears=pedal`) waits for TONE3000's word (below). |
| 2. A splash before sign-in | The TONE3000 tab, signed out: the full TONE3000 logo, their words (see "Asked of TONE3000"), and Continue. |
| 3. Sign-in through the Select flow | Continue opens TONE3000's own page (`prompt=select_tone`, `menubar=true`): email and 6-digit code, then their picker. |
| 4. Tone lists | Signed in, the tab shows the person's avatar and username, and tabs **Favorites, Created, Downloaded, Trending, Latest**, plus a search box. Every tone shows its image, title, gear type, format, creator (username and avatar) and licence; the view carries "Powered by TONE3000" with a link; a persistent **Browse TONE3000** button (the T3K mark) opens Select. |
| 5. A loaded tone on the signal chain | The amp's grille and a pedal's label show the tone's image and the T3K mark beside its title, gear type and creator, linked to the tone's page. |

Rig's star stays Rig's (the pads, D-RIG-024). A tone's **heart** is TONE3000's favourite (`PUT`/`DELETE
/tones/{id}/favorite`), shown only on TONE3000's cards and details.

## Signing in, in each build

- **Web:** a popup (480 by 700) to `/oauth/authorize` with `redirect_uri=https://rig.carbonlinear.com/tone3000.html`
  (`http://localhost:<port>/tone3000.html` when served locally). `tone3000.html` is a static page in `web/src` that
  hands `code`, `state`, `tone_id`, `error`, `canceled` back by `postMessage` to its opener, or by
  `BroadcastChannel('crbn-rig-t3k')` when the opener was cleared, then closes. If the popup is blocked, the same
  flow runs as a full-page redirect: `tone3000.html` keeps the callback in `sessionStorage` and returns to `/`.
- **Desktop:** the page calls the same `window.open`. The WebView2 host gives that window its own WebView2 (a popup
  owned by Rig's window, the same profile, so TONE3000's sign-in persists between flows), and allows only
  `https://www.tone3000.com` in it. Its redirect is `http://127.0.0.1/callback`, which the host catches in
  NavigationStarting **before any request is made**, cancels, and posts to the page as `{type:'t3kCallback', url}`;
  then it closes the popup. This is TONE3000's own JUCE example's WebView2 route. Any other link in it opens in the
  system browser.
- **Both:** PKCE S256, a fresh `state` per flow checked first; the verifier lives in memory (and `sessionStorage` for
  the web's full-page fallback). Tokens are kept in `localStorage` under `crbn-rig/tone3000` (access token, refresh
  token, expiry, the user's name and avatar), on this computer only. Refresh 60 s before expiry, single-flight,
  retry once on 401; a refresh refused with 400/401 ends the session (tokens cleared, the splash shown); network or
  5xx errors keep them. **Sign out** clears all of it. There is no revocation endpoint.

## Downloads, the library and offline play

- **Only on the person's request:** Play in a tone's details, or a pick returned by Select or Load Tone. Nothing is
  prefetched; images load lazily as cards come into view.
- `model_url` is fetched with the Bearer header, its host re-based on `https://www.tone3000.com` as TONE3000's
  clients do. The bytes play at once (the same `audio.loadSlot` / `loadIR` path as a library file).
- **Kept in the person's library folder,** so it plays offline and at the next launch:
  `TONE3000/<creator> - <tone title> (<tone id>)/<model name>.nam` (or `.wav`), unaltered, with one
  `tone3000.json` in that folder: tone id, title, url, gear, format, licence, creator (username, display name, url,
  avatar), image url, description's first lines, and each kept model's id, name, size, architecture and file name.
  The library reads it, so My folder shows the creator, licence and the T3K mark on these files, and a link to the
  tone. Nothing strips or changes creator, metadata or licence.
- **Web:** writing needs the picked folder in `readwrite`; Rig asks once, at the first download. A visit with no
  writable folder (files dropped, or none chosen) plays the capture and offers to choose a folder to keep it.
- **Desktop:** a new host message, `libWrite`, writes into the library folder (a temporary file, then a rename; only
  `.nam`, `.wav` and `tone3000.json`, under the same path guards as `libRead`). The folder watch then lists it.
- **Downloaded before:** a tone whose `tone3000.json` is already in the folder shows "In your library" and plays the
  local file; it is not fetched again.
- **Not built yet, asked of TONE3000 first:** rigs and share codes naming a TONE3000 capture by tone id and model id,
  so another person opening that rig gets it through **Load Tone** under their own account, never the file.

## Before TONE3000 signs off

TONE3000's terms have an integration like this reviewed before it is published. So until then, `tone3000.js`
`RELEASED` is false. The tab and the Browse buttons show only in a browser that opened Rig with `?tone3000`
(kept in that browser; `?tone3000=off` forgets it). TONE3000 reviews it on the live site, and players do not see it.
Their sign-off is one line: `RELEASED = true`. The desktop app has no query, so it shows TONE3000 only once
released. Its native half (the sign-in window, `libWrite`) is in and checked.

## Calls, and staying inside the limits

Every call is a person's action: opening the tab (one list page), a tab or page change, a search (debounced 400 ms,
at least two characters), opening a tone (`/tones/{id}`, `/models`), Play (one `model_url`), a heart. A client-side
limiter keeps Rig under 60 requests a minute per person (TONE3000's default is 100); a 429 waits and says so.
Search pages are 25, lists 24. No polling, no background refresh, no `/models/lookup` sweep of the person's folder.

- `web/src/tone3000-view.js`: the tab, splash, lists, search, details, model selector, hearts, Browse.

## Tests

TONE3000 has no sandbox. Tests never call it:

- **`web/check.mjs`** serves a recorded, made-up TONE3000 under `/__t3k/` (the API's documented shapes; tones and
  creators invented; NAM Core's example captures as the model files) and a fake authorize page that redirects back.
  The self-test signs in through the popup, lists every tab, searches, hearts, opens a tone, picks a model, plays it
  (equal to the engine run directly), finds it written to the folder with its `tone3000.json`, sees it credited in
  My folder, plays it again with the network refused, opens a rig that names it, and signs out.
- **`packaging/windows/check.mjs`** does the same against the native host: the popup caught at `127.0.0.1/callback`,
  `libWrite` and the watch.
- **Live, by hand, once per release:** a session signs in through the owner's own Chrome on `localhost` (the key's
  loopback is allowed) and plays one tone, at a few requests.

## Asked of TONE3000 in the review

- Their recommended splash words say Rig "has partnered with TONE3000"; their terms forbid implying a partnership
  without written approval. May Rig use their words as written once they sign off, or should it say "works with"?
- That keeping a person's requested captures in that person's own library folder, with `tone3000.json` beside them,
  for offline play, is the caching they allow.
- A production rate limit for Rig, and whether Rig's free, Hub-distributed status needs a commercial agreement.
- Whether a rig file naming tone ids (opened by another person through Load Tone) is welcome.
- Whether "Sign out" should also delete the person's kept captures (we think not: the person asked for them).
